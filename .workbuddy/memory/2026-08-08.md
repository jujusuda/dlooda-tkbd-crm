## SW 缓存导致用户看不到已部署的改动（排障）

### 现象
用户反馈"产品排序那些还是跟之前的一样都没变化"——8/2 已做的 4 项改动（排序/通过率表/邀约按品分组/日报明细）全部不可见。

### 根因
上一轮为"切换流畅"把 sw.js 改为 cache-first（缓存优先）。浏览器缓存了 8/2 之前的旧 JS/HTML，且 SW 脚本受浏览器 24h 更新限制 + HTTP 缓存影响，未及时换成新版，导致一直返回旧文件。

### 验证
- 用真实数据跑 `Data.sortByPositioning()`：排序前后顺序确实不同（爆品 2178/2190/2722 置顶，16 个撤退 SKU 置底），证明代码逻辑正确，问题纯在缓存。
- 档位分布：撤退16 / 爆品3 / 销售3 / 测品4（共26 SKU）。

### 修复（已上线）
- `sw.js`：CACHE_VERSION v2 → v3（强制重建缓存，丢弃旧文件）
- `app.js` SW 注册处新增：
  - `reg.update()` 主动检查更新（绕过 24h 限制）
  - `controllerchange` 监听 → 新 SW 接管后自动 `location.reload()` 一次（后续部署自动生效，无需手动清缓存）
- 已 `node -c` 通过；服务器 `curl /sw.js` 确认返回 v3。

### 用户侧操作
需**一次性硬刷新**（Ctrl+Shift+R / Mac Cmd+Shift+R）绕过 HTTP 缓存拿到 v3 SW，之后所有更新自动应用。

### 经验
PWA + 迭代开发时，cache-first 极易造成"改了看不到"。标准解：版本号 bump + controllerchange 自动重载。后续若再出现类似"没变化"，优先怀疑 SW 缓存而非代码。

## 第三轮：用户仍"没变化" → SW 改网络优先 + 一键清缓存 + 任务排序

### 现象
即便 v4 (SWR) + controllerchange 自动重载，用户反馈"还是没变化"。服务器 `curl` 确认已返回最新文件（product.js 含 sortByPositioning、task.js 含通过率、sw.js=v4）。说明用户浏览器仍卡在某旧 SW（v1/v2），其 cache-first 一直返回旧缓存，新 SW 未抢到控制权。

### 根因结论
cache-first / SWR 在"旧 SW 卡死"场景下不可靠：浏览器一旦被早期 SW 接管，若新 SW 因 24h 限制/HTTP 缓存未拿到，旧缓存永驻。自动重载依赖 controllerchange，而 controllerchange 只在"新 SW 真正接管"后触发——旧 SW 卡死则永不触发。

### 修复（已上线 v5）
- `sw.js`：CACHE_VERSION v4 → **v5**；fetch handler 从 SWR 改为 **Network-First（网络优先）**——每次都从服务器取最新文件，旧缓存彻底失效，仅离线时回退缓存。
- `js/app.js`：
  - 新增 **`?reset=1` 一键清缓存开关**：访问任意页面带该参数即 `unregister` 所有 SW + 清空 `caches`，然后自动刷新。
  - `reg.update()` 改为每 **60 秒**轮询一次（开发期迭代更顺）。
  - 保留 `controllerchange` 自动重载。
- `js/task.js`：寄样任务表新增**按定位排序**——`sortedTasks` 先按 `Data.getSKUPositionTier` 档位（爆品→销售→测品→撤退），同档内按优先级 P0→P1→P2，再按 SKU。

### 用户侧操作（关键）
1. **立刻验证（100% 有效）**：用**无痕/隐私窗口**打开 `http://localhost:8090`（手机用 Safari 隐私 / Chrome 隐身）。无痕窗口无旧 SW 缓存，直接加载最新 v5，立即看到全部改动。
2. **修常用浏览器**：打开 `http://localhost:8090/?reset=1`（或 `http://192.168.1.5:8090/?reset=1`，必须与正在用的 origin 一致）一键清缓存；或 DevTools → Application → Service Workers → Unregister 后 Ctrl+Shift+R；手机 PWA 移除图标重加。
3. 之后全自动：v5 网络优先 + 60s 自检，我改完刷新即见。

### 经验（重要）
- 对**持续迭代的内部工具**，SW 用 **network-first** 比 cache-first/SWR 稳妥得多，可彻底避免"改了看不到"。
- 给用户留**独立的清缓存开关（?reset=1）** + **无痕窗口验证法**，比指望浏览器自动更新可靠。
- 局域网 PWA 与 localhost 是**不同 origin / 不同 SW scope**，清缓存要对应 URL。

## 第七轮：上传 08-08 新 Excel 后"寄样任务消失" + "无恢复按钮" bug 修复

### 现象（用户上报）
上传新导出的 `hhhh (1).xlsx`（E:/download，765KB）后，寄样任务整页消失；且面板里没找到"恢复原始数据"按钮。

### 根因
1. **列名不匹配（主因）**：上传解析用**按列名精确查找**（`r['SKU']`/`r['目标量']`/`r['日均']`/`r['定位']`），而这次 08-08 飞书导出的表头被改成 **小写/新列名**：`sku` / `寄样量` / `平均每天` / `出单量7.29` / `有效期|天` / 产品定位表的 SKU 列实际叫「产品定位」。于是：
   - 寄样任务：`sku` 找不到 → `.filter(t=>t.sku)` 整页过滤掉 → **任务消失**
   - 产品定位：`SKU` 找不到 → SKU 整页消失
2. **"恢复原始"按钮默认 `display:none`**，仅在检测到已上传数据时才显示；而上传把空/错误数据写进 localStorage，用户卡在坏数据里、又看不到恢复入口。
3. 无"空表保护"：某张表解析为空也会整体覆盖，导致数据被清。

### 修复（已上线 v5 网络优先，无需 bump SW）
- `js/app.js` `buildFromSheets` 前新增 **`getCell(row, candidates)`**：先精确匹配、再**大小写不敏感**匹配；每张关键字段给**多个候选列名**（如 `sku`:['SKU','sku','产品定位']、`target`:['目标量','寄样量']、`avgDaily`:['日均','平均每天']、`validDays`:['有效期','有效期|天','有效期(天)'] 等），彻底兼容飞书不同导出版本的列名。
- 新增**安全合并**：每张表解析后若为空，则**保留原有（原始）该表数据**，不被空表覆盖；至少一张表非空才算成功。
- **"↩ 恢复原始数据"按钮改为始终显示**（之前条件显示易找不到），文案区分"有上传覆盖/无上传覆盖"两态。
- `node -c app.js` 通过；`curl` 确认 3000 已返回含 `getCell`/`安全合并`/`恢复为原始数据` 的新文件。

### 验证（用真实 `hhhh (1).xlsx` 跑 Python 模拟解析管线）
- 每日寄样 2843、暂定 214、邀约 383（SKU 正常）、**寄样任务 28 条**、**SKU 26 个** —— 之前消失的任务/SKU 现均正确解析。
- 注：`平均每天` 列在你这份导出里整列空（飞书未填），`avgDaily=None` 是真实数据，非 bug。
- openpyxl 需用 `read_only=False`（read_only=True 会漏读飞书导出数据，已知坑）。

### 经验
- 飞书导出的列名不稳定（大小写/中英/改名），前端解析必须**多候选 + 大小写不敏感**，不能用精确匹配。
- Excel 上传同步必须有**空表保护 + 恢复入口常驻**，否则一次坏上传会卡死用户。
