## v61 紧急修复：线上登录页无限重定向（真 bug，非缓存/口径问题）
- 用户截图 `dlooda-tkbd-crm.pages.dev/login?redirect=login%3Fredirect%3D...` 白屏。线上已部署 v60（说明用户已 Push），SW 仍是 v60、auth.js 仍是旧守卫。
- **根因**：Cloudflare Pages pretty URLs 把 `/login.html` 308 到 `/login`（实测 `/index.html`→`/` 也是 308），而 v60 守卫 `if (currentFile() === 'login.html') return;` 只认带 .html 的形式 → 在 `/login` 上误判为普通页 → 反复 `location.replace('login.html?redirect=' + 当前URL)` → 无限嵌套。本地 http.server 不做 308，所以本地预览测不出来。
- 修复提交 `5924869`（5 文件）：auth.js 三重登录页判定（html data-auth-page / __DLOODA_LOGIN_PAGE__ / URL 兼容 login 与 login.html）+ safeRedirect 清洗 + 8s 内 >3 次跳转熔断；login.html 加标记 + `history.replaceState` 把 /login 补回 /login.html（兼容旧守卫缓存）+ redirectTarget 加固；sw.js v61 + auth.js/auth-config.js/login* 强制 `cache:'no-store'`；audit_auth 23→39 项；audit_nav 版本断言改「≥v60」不再硬编码。
- 验证：写临时 `work/pretty_server.py` 复刻 308（`/xxx.html`→`/xxx`，`/` 不重定向，sw.js 返 404 避免 SW 干扰，OLD_AUTH=1 时返回 git show HEAD~… 的旧守卫），Chrome CDP 双场景实跑：新+新 停在登录页且登录成功回首页（7 组菜单在）；旧守卫+新登录页 也停住不循环。已清理临时文件与服务。
- 当前 `git status -sb` = `master...origin/master [ahead 1]`，**仍需用户 GitHub Desktop 再 Push 一次**；部署后建议无痕窗口或 `?reset=1` 打开。
- 经验：按 `location.pathname` 判断「当前是哪个页面」的逻辑，在 Cloudflare Pages 上必须兼容 pretty URLs（无 .html），否则会死循环；本地预览无法复现这类 308 问题，需专门模拟。

## 线上 414「还是没刷新出来」：不是没部署，是旧标签页的超长 URL
- 线上实测：`sw.js` = v61、`js/auth.js` 含 `isLoginPage` 且无旧判断、`/login` 三个标记齐全、干净地址 `/` `/login` `/?reset=1` 全 200。无头 Chrome 直连线上从 `/?reset=1` 进 → 3 次导航后停在登录页、登录成功回首页、7 组菜单齐全。
- 用户截图 HTTP ERROR 414：地址栏仍是死循环时期层层累积的 `login.html?redirect=login?redirect=...`，URL 超长 → 414。**刷新该标签页永远好不了**，必须关掉并手动输入干净地址；建议无痕窗口绕开旧 SW / 308 重定向缓存，且别点地址栏历史建议。
- ⚠️ 通用教训：修复重定向循环后，要主动告诉用户「别刷新旧标签页」，否则他会一直盯着那个已被浏览器记住的坏 URL，误以为没修好。
- 新发现边界 bug：从 `/?reset=1` 登录时，`redirectTarget()` 把纯查询串 `?reset=1` 拼成 `.html?reset=1`，URL 变成 `/.html?resetdone=1`（功能正常但 URL 错）。已改 `login.html` 只拆页面名补 `.html`（空/index → index.html）、`auth.js safeRedirect()` 纯 query 补首页；`audit_auth.js` 加 vm 抽取内联 `redirectTarget()` 的 11 项测试，39 → 50 PASS。提交 `3268485`，**当前 ahead 1，待用户下次 Push**（命令行 push 报 `could not read Username`，仍需 GitHub Desktop）。
